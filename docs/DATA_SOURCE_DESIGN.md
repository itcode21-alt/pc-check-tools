# 사이트 데이터 구조: 현황 조사와 개선 방향 (1단계 설계)

작성일: 2026-10-22. 이 문서는 "DB로 운영할지"를 검토하다가 **현재 구조를 직접 측정**한 결과를 정리한 것이다.
결론부터: **운영 DB로 옮기는 것은 권하지 않고, 이미 있는 "원본 1개 → 파생 파일" 구조를 정리하는 쪽이 맞다.**
다만 아래 "확인하지 못한 것"이 많아, 구조를 바꾸기 전에 그 부분부터 확인해야 한다.

## 1. 처음 진단을 정정한다

처음에는 "데이터 원본이 여러 곳이라 한 군데를 고치려면 여러 파일을 만져야 한다"고 진단했다. 측정해 보니 **절반만 맞았다.**

| 처음 진단 | 측정 결과 |
|---|---|
| 원본이 여러 곳에 있다 | **틀림.** `data.js`가 유일한 원본이고, `data-*.js` 분할 파일은 `scripts/split-data.mjs`가 만든 파생물이다(스크립트 주석에 명시). 오류 코드 162개, 증상 81개, 이벤트 코드 180개가 두 쪽에서 서로 빠진 것 없이 일치한다. |
| 페이지마다 데이터를 따로 쓴다 | **틀림.** 페이지에 내장된 `SITE_DATA`는 분할 파일의 항목과 필드까지 동일했다(`error-code-0x0000007b`로 확인). 내장 사본은 자동 생성물이다. |
| 데이터와 본문이 따로 쓰여 어긋난다 | **부분적으로만.** 오류 코드 98개 페이지에서 데이터의 `faq` 답변은 97%, `narrative`는 98개 중 96개가 페이지 본문에 그대로 있다. `checks`는 앞부분만 잘라 쓰는 등 가공되어 있다. |

## 2. 확인된 현재 구조

```
data.js (원본, 1.8MB, JS 객체 리터럴)
   │  scripts/split-data.mjs
   ├─ data-core / data-symptoms / data-symptom-details / data-error-codes / data-event-codes /
   │  data-board-parts / data-parts-catalog .js   (분할 파일, 표준 JSON)
   │  scripts/ (여러 생성기)
   └─ 각 HTML 안의 window.SITE_DATA 내장 사본 (228개 페이지, 합계 약 2.3MB)
      각 HTML 안의 STATIC_FALLBACK_START~END 정적 본문 (오류 코드 98개 모두, 증상 82개 중 70개)
```

- 이미 있는 파생물 점검: `scripts/check-derived-freshness.mjs`(KB가 원본과 어긋났는지), `check-page-data-sources.mjs`, `check-asset-versions.mjs`.
- `scripts/split-data.mjs`의 주석: "`data.js`를 유일한 원본(source of truth)으로 유지한 채 조각 파일을 파생".

## 3. 그러면 왜 표기 하나를 고치는 데 파일 18개를 만졌나

#43에서 "시작 복구" 표기를 보강할 때 `data.js` 1개, 분할 파일 2개, 정적 HTML 15개를 직접 고쳤다(`git show --stat`로 확인).
설계상으로는 원본 `data.js`만 고치고 파생물을 다시 만들면 되는 구조인데 그렇게 하지 못했다. **이유는 추정이다**(생성기를 실행해 보지 못했다). 가장 유력한 단서는 `scripts/generate-static-fallbacks.mjs`의 주석이다.

> 수기로 다듬은 페이지가 많아 기본 실행은 아무 페이지도 건드리지 않는다.

생성되는 구간(`STATIC_FALLBACK_START~END`) 안에 **사람이 손으로 다듬은 내용이 섞여 있을 가능성**이 있고, 그렇다면 다시 생성할 때 수작업이 사라진다. 그래서 원본과 생성물을 모두 손으로 맞춘 것으로 보인다. 즉 문제는 "원본이 여러 곳"이 아니라 **"생성 구간 안에 수작업이 섞여 있어 생성기를 신뢰할 수 없는 것으로 보인다"** 는 것이다. 이 가설은 4절의 측정으로 확인해야 한다.

## 4. 확인하지 못한 것 (구조를 바꾸기 전에 확인해야 함)

이 PC에는 Node가 없어서 생성기를 실행해 보지 못했다. 그래서 다음은 **모른다.**

1. **현재 정적 본문이 어느 생성기의 결과인가.** `generate-static-fallbacks.mjs`의 `errorFallback`은 `checks`를 `<li><strong>항목</strong> — 고정 설명</li>`로 만드는데, 현재 페이지는 `checks`의 앞 문장만 `<li>`에 넣고 뒤 문장을 "다음 단계"로 옮기는 다른 형식이다(`error-code-0x0000000a`에서 확인). 그러니 이 스크립트는 옛 버전이거나 다른 생성기 또는 수작업이 현재 본문을 만들었다. 어느 쪽인지 모른다.
2. **생성기를 다시 돌리면 현재 파일과 얼마나 달라지는가.** 측정하려면 Node에서 생성기를 실행하고 `git diff`를 봐야 한다.
3. **수작업 구간의 크기.** 98개 오류 코드 페이지 중 몇 개가 생성 결과와 달라졌는지 모른다.

비교 측정 한 번이 경향을 오판한 적이 있다. `checks`가 한 번은 49%, 한 번은 0/98로 나왔고 둘 다 비교 방식의 한계였다. **이 문서의 비율 수치는 근거로만 쓰고 결정에 쓰지 않는다.**

## 5. 개선 방향 (후보, 검증 후 결정)

### 권하지 않는 것: 운영 DB(요청 때마다 조회)
정적 파일이라 빠르고 검색 엔진에 그대로 보인다. DB를 거치면 느려지고, 편집 도구와 백업·보안이 새로 필요하며, 수작업 보강이 많은 398개 페이지를 구조화 데이터로 옮기는 비용이 크다. 지금 문제(생성 구간에 수작업이 섞임)는 DB로 풀리지 않는다.

### 후보 A (가장 작은 변경): 생성 구간과 수작업 구간을 눈으로 구분하기
- 생성기가 만드는 구간(`STATIC_FALLBACK_START~END`) 밖에 수작업 보강을 두는 규칙을 정한다. 이미 구간이 있으므로 새 파일 형식이 필요 없다.
- 수작업이 구간 **안**에 들어가 있는 페이지를 찾아 밖으로 옮기는 것이 선행 작업이다.
- 장점: 생성기를 다시 신뢰할 수 있게 된다. 단점: 기존 페이지를 하나씩 정리해야 한다.

### 후보 B: 생성기를 돌려 보고 차이를 측정만 하기 (먼저 할 일)
- Node가 있는 환경(예: GitHub Actions)에서 `generate-static-fallbacks.mjs --errors`를 임시 브랜치에 돌리고 `git diff --stat`으로 **어느 페이지가 얼마나 달라지는지**만 본다. 커밋하지 않는다.
- 이 측정이 4절의 1, 2, 3을 한꺼번에 답한다. 이것이 없으면 후보 A의 범위를 정할 수 없다.
- **측정 워크플로를 만들어 두었다**: `.github/workflows/measure-regeneration.yml`(수동 실행 전용). `contents: read` 권한만 있고 커밋·푸시 명령이 없어 저장소를 바꿀 수 없다.

**실행 방법**: GitHub의 Actions 탭 -> `Measure Regeneration` -> `Run workflow`. 이 워크플로 파일이 기본 브랜치(`main`)에 있어야 실행 버튼이 나타난다.
- `generator`: 측정할 생성기. 처음에는 `static-fallbacks-errors`(오류 코드 98개 페이지)를 권한다. 이어서 `static-fallbacks-symptoms`, `event-pages`, `game-pages`, `split-data`를 같은 방식으로 돌린다.
- `force`(기본 켬): 캡처가 있는 페이지도 덮어쓴다. **켜야 "생성기를 그대로 돌리면 캡처가 사라지는 페이지"가 보인다.** 끄면 보호 로직(#14)이 캡처 있는 페이지를 건너뛰어 그 페이지는 차이가 안 보인다.

**결과 읽는 법**(실행 요약 화면과 아티팩트 `measurement.md`, 전체 변경은 `regeneration.patch`):
- "달라지는 파일 수"와 "종류별 표": 생성기가 현재 파일을 얼마나 바꾸는가. 0이면 현재 페이지가 생성 결과와 같다는 뜻이고, 그러면 수작업이 생성 구간 안에 없다는 가설(3절)이 틀린 것이다.
- "캡처를 잃는 페이지": 생성기를 그대로 돌리면 사라지는 수작업의 직접 증거.
- "파일별 변화량의 분포": 중앙값이 작고 일부만 크면 몇몇 페이지에만 수작업이 몰려 있다는 뜻이다.
- 생성기가 오류로 끝나면 작업이 실패로 표시되고, 결과는 일부만 만들어진 상태일 수 있다.

**이 측정이 답하지 못하는 것**: 차이가 "생성기가 옛 버전이라서"인지 "수작업이 섞여서"인지는 구분하지 못한다. 차이가 큰 페이지 몇 개를 열어 `regeneration.patch`에서 어떤 줄이 바뀌는지 직접 읽어야 한다.

### 후보 C (이미 시작함): 어긋남을 자동으로 잡는 점검 추가
- `scripts/check-data-chunks.py`: `data.js`와 분할 파일의 항목이 일치하는지 점검(Node 없이 실행). 이 PR에 포함한다.
- 같은 방식으로 "내장 사본이 분할 파일과 일치하는지", "생성 구간이 생성기 결과와 일치하는지"를 점검으로 만들 수 있으나, 뒤의 것은 Node가 필요하다.

## 6. 권하는 순서

1. **후보 B**를 먼저 한다. Node가 있는 곳에서 측정만 한다(커밋 없음). 결과로 이 문서의 4절을 채운다.
2. 측정 결과가 "차이가 작다"면 **후보 A**로 간다. "차이가 크다"면 어느 구간이 수작업인지부터 분류한다.
3. **후보 C**는 B와 무관하게 지금부터 쓸 수 있다.

## 7. 이 PR에서 한 것

- `scripts/check-data-chunks.py` 추가(후보 C의 첫 점검). 시나리오 3개로 검증했다: 현재 상태 통과, 분할 파일에서 항목 1개를 지운 경우 실패, `data.js`의 키 이름이 바뀐 경우 조용히 통과하지 않고 실패.
- 이 설계 문서.
- **하지 않은 것:** 구조 변경, 생성기 실행, 페이지 수정. 위 4절을 확인하지 않은 채 구조를 바꾸면 수작업을 잃을 수 있다.
